# 업무 주기 (Work Cycle) & 검증 게이트

모든 구현 작업은 아래 주기를 따른다. 단계를 건너뛰거나 순서를 바꾸지 않는다.
E2E 검증의 상세 방법은 `skills/e2e-playwright/SKILL.md`를 따른다.

---

## 1. 작업 단위 주기 (Task Cycle) — 기능 1건마다 반복

작업 단위 = **API Route 1개 + 연결된 화면 1개**, 또는 **사용자가 요청한 개별 이슈/버그 해결 1건**, **하네스/설정 변경 1건** 등 독립적인 일정 업무 단위. 이보다 크면 쪼갠다. 검증(③~⑥) 통과 후 **⑧ 커밋까지 완료해야 작업이 종료**된다.

| # | 단계 | 해야 할 일 | 통과 기준 |
|---|---|---|---|
| ① | **착수** | PRD 해당 절 + Phase 스킬 + `harness-decisions.md` 확인. 작업 목표와 이번 작업의 완료 조건을 3줄 이내로 먼저 적는다 | 목표·완료 조건 명시 |
| ② | **구현** | 규칙(`rules/*`) 준수하여 코드 작성. 신규 로직(파서/정규화/토큰/암호화/타겟팅)은 단위 테스트를 **함께** 작성 | — |
| ③ | **정적 검증** | `npx tsc --noEmit` → `npm run lint` | 오류 0 |
| ④ | **단위 테스트** | `npm test` (vitest) | 전부 통과 |
| ⑤ | **E2E 검증 (headless)** | 영향받는 화면의 Playwright spec을 작성/갱신하고 실행: `npm run test:e2e -- <spec>` | 전부 통과. UI가 있는 작업은 E2E 없이 완료 불가 |
| ⑥ | **자가 점검** | 변경 파일의 쿼리에 `userId` 포함, 비밀값 비노출, 실제 발송 경로 차단 여부 확인 | 위반 0 |
| ⑦ | **보고** | 아래 「보고 형식」으로 결과 보고 | — |
| ⑧ | **커밋** | ③~⑥을 모두 통과한 작업 묶음을 아래 「5. 커밋 규칙」대로 **1개 커밋**으로 기록하고, 보고에 커밋 해시를 적는다 | 게이트 통과 상태로만 커밋 |

### 실패 처리
- ③~⑤ 실패 시 원인 수정 후 **③부터 다시** 실행한다.
- 같은 실패로 **수정 시도 3회**가 넘으면 멈추고, 실패 로그·원인 가설·시도한 내용을 보고한 뒤 사용자 판단을 받는다.
- 테스트를 통과시키려고 테스트를 삭제·`skip`·약화(단언 제거, timeout만 늘리기)하지 않는다. 테스트가 틀렸다고 판단되면 근거를 보고한다.

## 2. Phase 주기 (Phase Cycle) — Phase 1~5 각각

```
Phase 착수 ─▶ 작업 단위 주기 × N ─▶ Phase 게이트 ─▶ 사용자 승인 ─▶ 다음 Phase
```

### Phase 게이트 (모두 통과해야 Phase 완료)
1. `npx tsc --noEmit` / `npm run lint` / `npm test` 전부 통과
2. **E2E 전체 스위트 headless 실행** `npm run test:e2e` — 이전 Phase spec 포함(회귀 확인), 전부 통과
3. 해당 Phase 스킬 「완료 조건」 체크리스트 전 항목 충족
4. 규칙 준수 검토 (Claude Code: `harness-reviewer` 서브에이전트 / 그 외: `harness-reviewer` 점검 항목을 직접 수행) — 🔴 항목 0건
5. 검토 반영 수정이 있었다면 그 수정도 별도 커밋으로 남긴 뒤, Phase 결과 보고 → **사용자 승인 후** 다음 Phase 착수

## 3. 주기적 점검 (Recurring)

| 시점 | 수행 |
|---|---|
| 작업 단위 완료 시마다 | 영향 spec E2E (⑤) |
| 작업 단위 **3건마다** | E2E 전체 스위트 1회 (회귀 조기 발견) |
| 스키마/모델 변경 시 | E2E 전체 스위트 + 시드 재적재 확인 (`npm run seed`) |
| 의존성 추가·업그레이드 시 | `npm run build` + E2E 전체 스위트 |
| Phase 종료 시 | Phase 게이트 (위 2절) |

## 4. 보고 형식

```
## 작업: <작업명> (Phase N)
- 변경 파일: <목록>
- 정적 검증: tsc ✅ / lint ✅
- 단위 테스트: ✅ N passed
- E2E(headless): ✅ N passed  (spec: e2e/xxx.spec.ts)   ← 실패 시 ❌ + 실패 테스트명 + 원인
- 자가 점검: 테넌트 격리 ✅ / 비밀값 ✅ / 실제 발송 차단 ✅
- 커밋: <short-hash> <type>(<scope>): <subject>   (브랜치: <branch>)
- 남은 이슈 / 다음 작업: <...>
```
검증을 실행하지 못한 항목은 ✅로 쓰지 말고 `⏭ 미실행 (사유)`로 표기한다.

## 5. 커밋 규칙 — 업무 묶음마다 1커밋

### 5.1 커밋 시점 (업무 묶음의 정의)

| 업무 묶음 | 커밋 시점 | type 예시 |
|---|---|---|
| 작업 단위 주기 1건 (기능 + 그 테스트) | ⑧ — ③~⑥ 통과 직후 | `feat` / `fix` / `refactor` |
| 규칙 검토·리뷰 지적 반영 | 반영 후 게이트 재통과 시 | `fix` / `refactor` |
| 하네스 변경 (`.agents/`, `CLAUDE.md`, `.claude/`) | 변경 묶음 완료 시 — **코드와 섞지 않고 별도 커밋** | `docs(harness)` |
| 개발 도구·설정 (`.vscode/`, lint/test 설정, 의존성) | 설정 묶음 완료 시 | `chore(<대상>)` / `build(deps)` |
| 테스트만 추가·수정 | 해당 spec 통과 시 | `test(<scope>)` |
| 문서 (`README.md`, `docs/`) | 문서 묶음 완료 시 | `docs(<scope>)` |

- **한 커밋 = 한 목적.** 서로 다른 묶음(예: 기능 + 하네스 수정)을 한 커밋에 섞지 않는다. 섞였다면 경로별로 나눠 커밋한다.
- **게이트를 통과하지 못한 상태는 커밋하지 않는다** (WIP 커밋 금지). 중간 저장이 필요하면 사용자에게 묻는다.
- **일정 업무별 커밋 의무화**: 사용자가 지시한 일정 업무(기능 구현, 버그/이슈 수정, 하네스/설정 변경 등)가 끝나면 미커밋 상태로 남겨두지 않고 **반드시 커밋을 실행**한다. 여러 작업 단위를 몰아서 한 번에 커밋하지 않고, 작업 단위가 끝날 때마다 커밋한다.

### 5.2 브랜치 · 원격

- 릴리스 브랜치(`main`/`master`)에는 직접 커밋하지 않는다. 그 위에 있으면 작업 브랜치 `work/<phase|topic>` (예: `work/phase3-contacts`)를 만들어 커밋한다.
- 사용자가 체크아웃해 둔 그 외 브랜치(예: `develop`, `feature/*`)는 사용자가 고른 작업 브랜치로 보고 **그대로 커밋**한다. 브랜치를 임의로 바꾸지 않는다.
- `push`, 병합, PR 생성은 **사용자가 요청할 때만** 한다.
- `--amend`, `rebase`, `reset --hard`, `push --force` 등 이력 재작성은 사용자 요청 없이 하지 않는다. 커밋 후 수정이 필요하면 새 커밋을 만든다.

### 5.3 커밋 전 점검

1. `git status` 로 변경 목록을 확인하고, **이번 묶음의 파일만 경로를 지정해** 스테이징한다 (`git add -A` / `git add .` 금지).
2. 다음은 절대 커밋하지 않는다: `.env.local` 등 비밀 파일, `.next/`, `test-results/`, `playwright-report/`, `e2e/.auth/`, `*.tsbuildinfo` — `git diff --cached --name-only` 로 최종 확인.
3. **작업 전부터 있던 사용자의 미커밋 변경은 포함하지 않는다.** 이번 묶음과 같은 파일에 사용자 변경이 섞여 있으면 커밋하지 말고 사용자에게 알린다.
4. pre-commit 훅이 실패하면 `--no-verify` 로 우회하지 말고 원인을 고친 뒤 새로 커밋한다.

### 5.4 메시지 형식

`rules/coding-conventions.md` 「커밋 메시지」 형식(`<type>(<scope>): <subject>`, subject 는 한국어·명령형 요약·50자 내외)을 따른다. 본문에는 **무엇을 왜** 바꿨는지와 검증 결과(tsc/lint/unit/E2E 통과 수)를 적는다. 에이전트 도구가 요구하는 서명(예: `Co-Authored-By`) 트레일러는 본문 끝에 유지한다.
